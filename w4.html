Operating Systems — Concurrency, Synchronization & Deadlocks

1. Concurrency and Synchronization

1.1 Concurrency

  • Concurrency = Multiple processes/threads execute during overlapping time periods.
  • When processes share data/resources, incorrect results can occur unless their access is properly synchronized.
  • Synchronization = Coordinating processes so that shared data remains consistent.

2. Producer-Consumer Problem

The Producer-Consumer Problem is a classic synchronization problem involving a shared buffer.

Shared Buffer
+-------------------------------+--------+
Producer | [ ][ ][ ][ ][ ] Buffer | Consumer
 --->    | Adds data     Removes data |  --->   
+-------------------------------+--------+
  • Producer: Generates data and puts it into the shared buffer.
  • Consumer: Takes data from the shared buffer and processes it.

Main Challenges

  • Producer must not add data when the buffer is full.
  • Consumer must not remove data when the buffer is empty.
  • Producer and consumer must not access the buffer in a conflicting way at the same time.

2.1 Producer Code

while (true) {
    /* produce an item in next_produced */
    while (counter == BUFFER_SIZE)
        ; /* do nothing */

    buffer[in] = next_produced;
    in = (in + 1) % BUFFER_SIZE;
    counter++;
}

2.2 Consumer Code

while (true) {
    while (counter == 0)
        ; /* do nothing */

    next_consumed = buffer[out];
    out = (out + 1) % BUFFER_SIZE;
    counter--;

    /* consume the item in next_consumed */
}
Important: counter = Number of items currently present in the buffer.
counter = 0 → Buffer Empty
0 < counter < N → Buffer Partially Full
counter = N → Buffer Full

3. Race Condition

Definition

A Race Condition occurs when multiple processes access and modify shared data concurrently, and the final result depends on the order in which their instructions execute.

Example

Suppose counter = 5

counter++ may internally execute as:

register1 = counter
register1 = register1 + 1
counter = register1

counter-- may internally execute as:

register2 = counter
register2 = register2 - 1
counter = register2

Problematic Interleaving

Initial: counter = 5

S0: Producer -> register1 = counter          (register1 = 5)
S1: Producer -> register1 = register1 + 1    (register1 = 6)
S2: Consumer -> register2 = counter          (register2 = 5)
S3: Consumer -> register2 = register2 - 1    (register2 = 4)
S4: Producer -> counter = register1          (counter = 6)
S5: Consumer -> counter = register2          (counter = 4)
  • Expected Result: One increment and one decrement should cancel each other (5 + 1 - 1 = 5).
  • Actual Result: counter = 4 (The shared variable has become inconsistent).
Exam Point: Race conditions occur because operations on shared data can be interleaved unpredictably.

4. Critical Section Problem

4.1 Critical Section

A Critical Section (CS) is the part of a process where shared resources/data are accessed or modified.

Examples: Updating common variables, Updating a shared table, Writing to a shared file, Accessing a shared buffer.

If one process is executing its critical section, another process should not execute its conflicting critical section simultaneously.

4.2 General Process Structure

+---------------------+
|    Entry Section    |
|   (Request access)  |
+----------+----------+
           |
           v
+---------------------+
|   Critical Section  |
|   (Shared resource) |
+----------+----------+
           |
           v
+---------------------+
|    Exit Section     |
|   (Release access)  |
+----------+----------+
           |
           v
+---------------------+
|  Remainder Section  |
|     (Other work)    |
+---------------------+
Section Purpose
Entry Request permission to enter CS
Critical Access shared resource
Exit Release/leave CS
Remainder Execute other code

5. Requirements for Critical-Section Solution

A correct solution must satisfy three requirements.

5.1 Mutual Exclusion

If process Pi is executing in its critical section, no other process can execute its critical section at the same time.

P0 → [ CRITICAL SECTION ] | P1 → Cannot enter CS

5.2 Progress

If no process is currently in the critical section and some processes want to enter, the selection of the next process cannot be postponed indefinitely.

5.3 Bounded Waiting

There must be a limit on how many times other processes can enter their critical sections after a process has requested entry and before its request is granted.

Assumptions: Each process executes at a nonzero speed. No assumption is made about the relative speed of processes.

Fingertip:
Mutual Exclusion → Only one inside CS
Progress → Don't postpone entry forever
Bounded Waiting → Don't make a process wait forever

6. Peterson's Solution

Peterson's Solution is an algorithmic solution to the critical-section problem for two processes.

  • Assumes: Two processes (P0 and P1). Load/store instructions are atomic.

Two shared variables are used:

int turn;
Boolean flag[2];
  • turn: Indicates whose turn it is to enter the critical section.
  • flag[i]: Indicates whether process Pi wants to enter the critical section (flag[i] = true).

6.1 Peterson's Algorithm for P0

do {
    flag[0] = true;
    turn = 1;

    while (flag[1] && turn == 1)
        ;

    // critical section

    flag[0] = false;

    // remainder section
} while (true);

6.2 Peterson's Algorithm for P1

do {
    flag[1] = true;
    turn = 0;

    while (flag[0] && turn == 0)
        ;

    // critical section

    flag[1] = false;

    // remainder section
} while (true);

6.3 Why Peterson's Solution Works

  1. Mutual Exclusion: P0 enters CS only when flag[1] == false OR turn == 0. The while condition ensures that both cannot enter simultaneously.
  2. Progress: P0 waits only when flag[1] == true AND turn == 1. If the other process does not want to enter, P0 can proceed.
  3. Bounded Waiting: Once a process sets its flag to true, the other process can enter the critical section at most one more time before the waiting process gets its turn.
Fingertip: Peterson's Solution
• flag[] → Who wants to enter?
• turn → Whose turn?
• Two-process solution
• Satisfies: Mutual Exclusion, Progress, Bounded Waiting

7. Mutex Locks

Definition

A Mutex Lock is a synchronization mechanism used to protect a critical section.

A process must acquire and release a mutex lock around its critical section:

acquire() → Critical Section → release()

The lock is represented by a Boolean-like variable indicating whether it is available.

7.1 acquire() and release()

acquire() {
    while (!available)
        ; /* busy wait */
    available = false;
}

release() {
    available = true;
}

Important: acquire() and release() must be atomic (generally implemented using hardware atomic instructions).

7.2 Spinlock

Mutex locks using busy waiting are called spinlocks. CPU time is wasted while waiting.

Important Rule: The same thread/process that performs acquire() should perform release().

8. Semaphore

Definition

A Semaphore is a synchronization tool that provides more sophisticated process synchronization than simple mutex locks. A semaphore S is an integer variable accessed only through atomic operations:

  • wait(S) (Originally P())
  • signal(S) (Originally V())

8.1 wait()

wait(S) {
    while (S <= 0)
        ; /* busy wait */
    S--;
}

8.2 signal()

signal(S) {
    S++;
}
Fingertip:
wait() → Decrease semaphore / wait if unavailable
signal() → Increase semaphore / release resource

9. Types of Semaphores

Type Values Typical Use
Counting Semaphore 0, 1, 2, 3, ... Multiple instances of a resource
Binary Semaphore 0 or 1 Mutual exclusion (like a mutex lock)

10. Semaphore for Process Ordering

Suppose S1 must happen before S2. Create: semaphore synch = 0;

P1:                 P2:
    S1;                 wait(synch);
    signal(synch);      S2;

S1 → signal(synch) → wait(synch) → S2

Therefore: S1 always happens before S2.

11. Deadlock & 12. Example Using Semaphores

Definition

Deadlock occurs when two or more processes wait indefinitely for events/resources that can only be caused/released by the waiting processes.

Simple Example

Initially: S = 1, Q = 1

P0                  P1
wait(S)             wait(Q)
   |                   |
   v                   v
holds S             holds Q
   |                   |
wait(Q)             wait(S)
   |                   |
   v                   v
 WAIT                WAIT
  • P0 holds S and waits for Q.
  • P1 holds Q and waits for S.
  • Neither process can continue.

13. Starvation

Definition

Starvation = Indefinite blocking of a process. A process may wait indefinitely because it is never selected or removed from the semaphore/resource waiting queue.

Deadlock vs Starvation

Deadlock Starvation
Processes wait for each other A process waits indefinitely
Usually involves circular waiting Can occur due to unfair scheduling
Multiple processes permanently blocked One process may continuously be denied access
Fingertip:
Deadlock → Everyone involved is stuck
Starvation → A process may never get its turn

14. Necessary Conditions for Deadlock

Deadlock can occur only when all four conditions hold simultaneously:

           +----------------------+----------------------+
           |                      |                      |
           v                      v                      v
    Mutual Exclusion        Hold & Wait            No Preemption
                              |
                              v
                        Circular Wait

14.1 Mutual Exclusion

At least one resource must be non-sharable. Only one process can use that resource at a time.

14.2 Hold and Wait

A process is holding at least one resource while waiting to acquire another resource held by another process.

14.3 No Preemption

A resource cannot be forcibly taken away from a process. It must be released voluntarily by the process holding it.

14.4 Circular Wait

A circular chain of waiting processes exists:

P0 waits for R1 (held by P1) → P1 waits for R2 (held by P2) → P2 waits for R3 (held by P0)

Exam Point: Deadlock requires ALL FOUR conditions to hold simultaneously.

15. Traffic Example of Deadlock

A traffic intersection jam demonstrates all four deadlock conditions:

       Vehicle A
           |
           v
     +-----------+
     |   Road    |
     +-----------+
           |
           v
        Vehicle B
           |
           v
        Vehicle C ---> (Waiting in circular chain)
  1. Mutual Exclusion: Only one vehicle can occupy a particular road section at a time.
  2. Hold and Wait: Each vehicle occupies one section while waiting for another section.
  3. No Preemption: A road section occupied by a vehicle cannot simply be taken away.
  4. Circular Wait: Each vehicle waits for a section occupied by another vehicle in the circular chain.

16. Methods for Handling Deadlocks

There are four major approaches to handling deadlocks:

  1. Deadlock Prevention: Prevent at least one of the four necessary conditions from occurring.
  2. Deadlock Avoidance: Use additional information about future resource requirements and allocate resources only if the resulting state remains safe.
  3. Deadlock Detection and Recovery: Allow deadlocks to occur, detect them, and then recover.
  4. Do Nothing: If a system does not use prevention, avoidance, or detection/recovery, deadlocks may occur and remain.

17. Deadlock Prevention

Deadlock prevention works by restricting how resources can be requested. The goal is to ensure that at least one necessary condition cannot hold.

17.1 Prevent Mutual Exclusion

  • Cannot always be eliminated (non-sharable resources require mutual exclusion).
  • For sharable resources (e.g., read-only files), sharing is possible.

17.2 Prevent Hold and Wait

  • Require a process to request all required resources before execution begins, OR
  • Allow a process to request resources only when it currently holds no resources.
  • Disadvantages: Low resource utilization, starvation may occur.

18. Deadlock Prevention — No Preemption

If a process holding some resources requests another resource that cannot be immediately allocated, then all resources currently held by that process may be released.

P0 (Holds R1+R2) → Requests R3 (Unavailable) → Release R1+R2 → Wait for R1+R2+R3 → Restart when all obtained

  • Currently held resources are released.
  • Preempted resources are added to the list of resources for which the process is waiting.
  • The process restarts only when it can regain its old resources and the newly requested resources.

19. Deadlock Prevention — Circular Wait

Circular wait can be prevented by imposing a total ordering on all resource types. Each resource type is assigned a number (e.g., Tape=1, Disk=5, Printer=12).

Rule: A process must request resources in increasing order. If it has requested Ri, it can request Rj only if F(Rj) > F(Ri).

  • Valid: Tape drive (1) → Disk drive (5) → Printer (12)
  • Invalid: Printer (12) → Disk drive (5) (because 5 < 12)
Exam One-Liner: Circular wait is prevented by imposing a total ordering on resource types and requiring every process to request resources in increasing order.

20. Deadlock Avoidance

Deadlock Avoidance requires additional information about the maximum resources each process may need. The OS dynamically checks every resource request.

Process Requests Resource
           |
           v
 Check Resulting State
           |
+-----------------+-----------------+
|                                   |
v                                   v
Safe State                     Unsafe State
(Allocate Resource)               (Wait)
  • Each process must declare its maximum resource requirement in advance.
  • The system decides whether granting a request keeps the system in a safe state.

21. Resource-Allocation State & 22. Safe State & 23. Safe vs Unsafe

Resource-Allocation State: Defined by available resources, allocated resources, and maximum resource demands.

Safe State

A system is in a safe state if there exists an ordering of all processes <P1, P2, ..., Pn> (a safe sequence) such that every process can obtain its remaining required resources, finish, and release its resources.

Available Resources → Can P1 finish? (Yes) → P1 finishes & releases → Can P2 finish?...

Safe vs Unsafe State

State Meaning
Safe State System has at least one safe sequence (No deadlock)
Unsafe State No guaranteed safe sequence (Deadlock is possible)
Deadlock State Processes are actually permanently blocked
Fingertip:
Safe → Deadlock guaranteed to be avoidable
Unsafe → Deadlock may occur
Deadlock → Deadlock has occurred

24. Banker's Algorithm & 25. System Model

Banker's Algorithm is a deadlock-avoidance algorithm.

  • Used when multiple instances of each resource type exist.
  • Each process declares its maximum resource requirement.
  • A process may need to wait for resources, and must eventually return all allocated resources.

System Model: A process uses resources in this order: Request → Use → Release

26. Banker's Algorithm Example & 27. Need Matrix

5 processes (P0-P4), 3 resource types (A=10, B=5, C=7).

Snapshot at T0: Available = (3, 3, 2)

Need Matrix

Need = Max - Allocation

Process Allocation (A B C) Max (A B C) Need (A B C)
P0 0 1 0 7 5 3 7 4 3
P1 2 0 0 3 2 2 1 2 2
P2 3 0 2 9 0 2 6 0 0
P3 2 1 1 2 2 2 0 1 1
P4 0 0 2 4 3 3 4 3 1

28. Safe Sequence in Banker's Algorithm

Initial: Available = (3, 3, 2)

  1. P1: Need (1,2,2) ≤ Available (3,3,2) → Finishes. New Available = (3,3,2) + (2,0,0) = (5,3,2)
  2. P3: Need (0,1,1) ≤ Available (5,3,2) → Finishes. New Available = (5,3,2) + (2,1,1) = (7,4,3)
  3. P4: Need (4,3,1) ≤ Available (7,4,3) → Finishes. New Available = (7,4,3) + (0,0,2) = (7,4,5)
  4. P2: Need (6,0,0) ≤ Available (7,4,5) → Finishes. New Available = (7,4,5) + (3,0,2) = (10,4,7)
  5. P0: Need (7,4,3) ≤ Available (10,4,7) → Finishes.
Safe sequence: <P1, P3, P4, P2, P0>
Hence: System is in a SAFE STATE

29. Banker's Algorithm — Fingertip Method

  1. Calculate Need: Need = Max - Allocation
  2. Start with Available
  3. Find a process where Need <= Available
  4. Assume it finishes
  5. Add its Allocation to Available
  6. Repeat

If ALL processes finish → SAFE STATE. If no process can finish → UNSAFE STATE.

32. Most Important Exam Concepts

  • Critical Section: Entry → Critical → Exit → Remainder
  • Three CS Requirements: Mutual Exclusion, Progress, Bounded Waiting
  • Peterson's Solution: Two processes, flag[], turn
  • Mutex: acquire() → Critical Section → release()
  • Semaphore: wait(S), signal(S)
  • Deadlock Conditions: Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait
  • Deadlock Prevention: Break at least ONE necessary condition
  • Deadlock Avoidance: Never enter an unsafe state
  • Banker's Algorithm: Need = Max - Allocation
  • Safe State: At least one safe sequence exists

33. Exam One-Liners

  • Race Condition: A situation where the final result depends on the order of concurrent execution of processes.
  • Critical Section: The part of a process that accesses shared data/resources.
  • Mutual Exclusion: Only one process can execute a critical section at a time.
  • Progress: If the critical section is free, selection of the next process cannot be postponed indefinitely.
  • Bounded Waiting: A process must have a finite bound on how many times others can enter before it gets its turn.
  • Peterson's Solution: A software solution for the critical-section problem involving two processes using flag[] and turn.
  • Mutex Lock: A synchronization mechanism that protects a critical section using acquire() and release().
  • Spinlock: A lock where a process continuously waits by busy waiting.
  • Semaphore: An integer synchronization variable accessed through atomic wait() and signal() operations.
  • Deadlock: A state where processes wait indefinitely for resources/events held or controlled by other waiting processes.
  • Starvation: Indefinite waiting of a process because it is repeatedly denied access to a resource.
  • Deadlock Prevention: Preventing at least one of the four necessary deadlock conditions.
  • Deadlock Avoidance: Dynamically allocating resources while ensuring the system remains in a safe state.
  • Safe State: A state in which there exists a safe sequence allowing all processes to finish.
  • Banker's Algorithm: A deadlock-avoidance algorithm that checks whether granting resources keeps the system safe.
  • Need Matrix: Need = Max - Allocation.
  • Circular Wait Prevention: Assign a numerical order to resource types and require processes to request resources in increasing order.
  • No Preemption Prevention: If a requested resource cannot be immediately allocated, a process may be forced to release resources it currently holds.
