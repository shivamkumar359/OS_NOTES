Operating Systems — Fingertip Concise Notes

1. What is an Operating System?

Operating System (OS): Software that acts as an intermediary between the user and computer hardware.

Two Views of OS

View Meaning
User-centric Provides an easy interface and services to users
System-centric Allocates resources and controls system operations
Exam Point: OS = Resource Allocator + Control Program + Interface

2. Computer System Structure

A computer system has 4 main components:

  1. Hardware: CPU, memory, I/O devices
  2. Operating System: Controls and coordinates hardware
  3. Application Programs: Word processors, browsers, compilers, DBMS, games
  4. Users: People, machines, other computers
Fingertip: Hardware → OS → Applications → Users

3. What Does an OS Do?

Depends on the type of system.

  • Provides convenience
  • Improves performance
  • Manages system resources
  • Supports multiple users/programs
  • Optimizes battery life in handheld systems
  • Embedded systems may have little/no user interface

4. Computer Startup

At power-up/reboot:

Bootstrap Program → Initializes System → Loads OS Kernel → Starts Execution

Bootstrap Program

  • Stored in ROM/EPROM
  • Also called firmware
  • Loads the OS kernel into memory
Exam: Bootstrap program is the first program executed during startup.

5. Computer-System Operation

  • CPU and I/O devices can work concurrently.
  • Each device has a device controller.
  • Controller has a local buffer.
  • Data moves between main memory ↔ local buffer.
  • After completing an operation, the controller sends an interrupt to the CPU.
Fingertip: Device → Controller → Buffer → Memory → Interrupt

6. Storage Hierarchy

Storage systems are organized as a hierarchy based mainly on:

  • Speed
  • Cost
  • Volatility

Faster storage is generally more expensive and smaller.

7. Caching

Caching: Copying information from slower storage to faster storage temporarily.

How it works

  1. Check faster storage (cache).
  2. If data is present → use it directly.
  3. If absent → copy data from slower storage to cache.
  4. Use the cached copy.

Cache is smaller than the storage it represents.

Important cache issues

  • Cache size
  • Replacement policy
  • Cache management
Fingertip: Cache = Small + Fast + Temporary copy

8. Device Driver

Device Driver: Software that manages a particular device controller.

It:

  • Manages I/O devices
  • Provides a uniform interface between the device controller and OS kernel

9. Multiprogramming

Multiprogramming: Keeping multiple jobs in memory so the CPU always has something to execute.

Why?

A single program may wait for I/O, leaving the CPU idle.

Working

Job A running → A waits for I/O → OS switches to Job B

Goal: Improve CPU utilization and efficiency.

10. Timesharing / Multitasking

Timesharing: Extension of multiprogramming where the CPU switches between jobs very frequently.

This allows users to interact with programs while they are running.

  • Provides interactive computing
  • Response time should generally be < 1 second
  • Each user has at least one program in memory → Process
  • If multiple jobs are ready → CPU Scheduling is required.

Difference

Multiprogramming Timesharing
Focuses on CPU utilization Focuses on interactive response
Switches when job waits Switches frequently
Mainly efficiency Mainly user interaction

11. Operating-System Operations

OS operation is interrupt-driven.

Types of Interrupts

  1. Hardware Interrupt: Generated by hardware/device.
  2. Software Interrupt: Also called exception/trap.
    • Examples: Division by zero, Request for OS service, Other process-related problems.

12. Dual-Mode Operation

Used to protect the OS and other system components.

Two modes:

  1. User Mode
  2. Kernel Mode

Mode Bit: Hardware mechanism that identifies the current mode.

Privileged Instructions

Certain instructions can only execute in kernel mode.

Mode Transition

User Program → System Call → Kernel Mode → Return → User Mode

Exam: Privileged instructions cannot be executed directly in user mode.

13. Major Tasks of OS

The OS mainly manages:

  1. Process Management
  2. Memory Management
  3. I/O Management
  4. File Management
  5. Storage Management
  6. Protection & Security

14. Process Management

Process: A program in execution.

Program Process
Passive entity Active entity
Stored code Code currently executing
No execution state Has execution state/resources

A process may require: CPU, Memory, I/O, Files, Initialization data.

When a process terminates, OS must reclaim its resources.

OS Process Activities

  • Create/delete processes
  • Suspend/resume processes
  • Process synchronization
  • Process communication
  • Deadlock handling

15. Memory Management

To execute a program:

  • Instructions must be in memory.
  • Required data must be in memory.

Memory Management: Determines what is in memory and when.

Main Activities

  • Track used/free memory
  • Decide what enters/leaves memory
  • Allocate memory
  • Deallocate memory
  • Improve CPU utilization and response time

16. Storage & File-System Management

OS provides a logical view of storage: Physical storage → File

File-System Activities

  • Create/delete files
  • Create/delete directories
  • Manipulate files/directories
  • Map files to secondary storage
  • Backup files
  • Access control

Files are usually organized into directories.

17. I/O Management

OS hides hardware-specific details from users.

I/O subsystem handles:

  • Buffering: Temporary storage while data is transferred.
  • Caching: Stores frequently/actively used data in faster storage.
  • Spooling: Overlaps output of one job with input of another.

Also provides:

  • General device-driver interface
  • Device-specific drivers
Fingertip:
Buffer = Temporary transfer storage
Cache = Faster copy for performance
Spool = Overlap I/O operations

18. Protection & Security

  • Protection: Controls access of processes/users to system resources.
  • Security: Protects the system from internal and external attacks. (Examples: Viruses, Worms, Denial-of-service, Identity theft, Theft of service)

User Identification

  • User ID: Identifies a user
  • Group ID: Identifies a group of users
  • IDs are associated with files/processes to control access.
  • Privilege escalation: Changing to an ID with greater permissions.
Exam:
Protection = Access control
Security = Defense against attacks

19. User Interfaces

CLI — Command Line Interface

Allows users to directly enter commands.

  • Shell: Fetches commands, Executes commands, Can have different implementations (Examples include Unix/Linux shells).

GUI — Graphical User Interface

Uses: Mouse, Keyboard, Monitor, Icons, Windows/folders.

Many operating systems support both CLI and GUI.

Touchscreen Interface

Uses: Gestures, Virtual keyboard, Touch-based selection, Voice commands.

20. System Calls

System Call: Programming interface through which programs request services from the OS.

Programs usually access system calls through APIs.

Common APIs

  • Windows API
  • POSIX API
  • Java API
Fingertip: Application → API → System Call → OS

21. Types of System Calls

Type Examples
Process Control Create, terminate, execute, wait, allocate/free memory, locks
File Management Create, delete, open, close, read, write, reposition, get/set attributes
Device Management Request/release device, read/write, attach/detach devices
Information Maintenance Get/set time, system/process/file information
Communication Send/receive messages, shared memory
Protection Access control, permissions

Communication

Two major approaches:

  1. Message Passing: Processes send/receive messages.
  2. Shared Memory: Processes share memory regions.

22. UNIX Structure

Traditional UNIX structure is:

  • More than a simple structure
  • Not completely layered
  • Contains a UNIX kernel

23. OS Impact on AI/Data Science

Modern AI/DS workloads depend heavily on OS functionality.

Process & Thread Management

  • Training uses multiple processes/threads.
  • OS scheduler affects: Training time, Latency, CPU-GPU overlap, GPU utilization.

Memory Management

  • AI models require large amounts of memory.
  • OS manages: Virtual memory, Page faults, Shared memory.
  • Problems: Excessive swapping → slower training; Memory fragmentation → allocation failures.

File System & I/O

  • Training data may be read repeatedly across epochs (e.g., ImageNet, CSV/Parquet, TFRecords, WebDataset).
  • Therefore: Caching + Buffering → Important for training performance.
  • Important techniques:
    • mmap(): Maps a file into virtual memory.
    • Prefetching: Loads the next batch while the current batch is being processed.

24. GPU & Accelerator Interaction

OS manages:

  • GPU drivers
  • DMA transfers
  • Context switching

OS/kernel scheduling affects GPU utilization. NUMA-aware memory placement can improve performance.

25. Networking for Distributed AI

Distributed training uses:

  • Sockets
  • RDMA
  • TCP/IP
  • RoCE

OS networking affects: All-reduce latency, Parameter synchronization speed.

Note: RDMA/kernel bypass → Lower latency than traditional sockets.

26. Containers & MLOps

Tools such as Docker and Kubernetes depend on OS features.

Important OS mechanisms:

  • Namespaces: Isolation
  • cgroups: Resource control
  • Virtual file systems

OS can enforce: CPU limits, GPU limits, Memory limits, Job isolation.

Operating Systems — Processes & Threads (Week 2)

1. Process Concept

Process Definition

  • Process = a program in execution.
  • A program is a passive file stored on disk.
  • A process is an active program executing in memory.
  • A program becomes a process when it is loaded into memory.
  • One program can create multiple processes when executed by different users.

Process Components

Part Purpose
Text/Code section Program instructions
Program Counter + Registers Current execution activity
Stack Function parameters, return addresses, local variables
Data section Global variables
Heap Dynamically allocated memory
Key Distinction: A program is passive (stored on disk), whereas a process is active (executing in memory).

2. Process States

As a process executes, it moves through different states:

State Meaning
New Process is being created
Running Instructions are being executed
Waiting Waiting for some event
Ready Waiting for CPU assignment
Terminated Execution is finished
State Transitions: New → Ready → Running → Waiting → Ready → Terminated

3. Process Control Block (PCB)

Definition

PCB = data structure containing information about a process. Also called Task Control Block (TCB).

PCB contains:

  • Process State → running, waiting, etc.
  • Program Counter → next instruction to execute
  • CPU Registers → register contents
  • CPU Scheduling Information → priority, queue pointers
  • Memory Management Information → memory allocated
  • Accounting Information → CPU time, elapsed time, limits
  • I/O Status Information → allocated devices, open files
Note: PCB stores all execution-related data required to manage a process.

4. Context Switch

Definition

When CPU changes from one process to another:

Save old process state → Load new process state

  • Process context is stored in the PCB.
  • Context-switching consumes CPU time.
  • During switching, no useful process work is performed.
  • More complex OS/PCB → potentially longer switch time.
  • Time depends on hardware support.
Summary: Context Switch = Save Old + Load New
Note: Context switching represents overhead because the CPU performs no productive work during the switch.

5. Process Creation

  • A parent process can create child processes.
  • Children can create more processes → forms a process tree.
  • Every process is identified by a PID (Process ID).

Resource Sharing

Parent and child may:

  • Share all resources
  • Share a subset
  • Share no resources

Execution

  • Parent and child execute concurrently OR
  • Parent waits until child terminates.

UNIX

  • fork() → creates a new process
  • exec() → replaces process memory with a new program
Summary: fork() creates a new process; exec() replaces the process memory with a new program.

6. Process Termination

Normal termination

  • Process finishes its last statement.
  • Calls exit().
  • OS deallocates its resources.
  • Parent can obtain child status using wait().

Parent can terminate a child using abort() when:

  • Child exceeds allocated resources.
  • Child's task is no longer required.
  • Parent terminates and OS does not allow child to continue.

7. Zombie and Orphan Processes

Zombie Process

  • A terminated child whose parent has not yet called wait().
  • Child's process-table entry remains.
  • Exit status has not yet been collected.

Orphan Process

  • A child whose parent terminates without calling wait().
  • OS assigns the init process as its parent.
  • init periodically calls wait().

Zombie vs Orphan

Zombie Orphan
Child already terminated Child is still running
Parent has not collected status Parent has terminated
Entry remains in process table Adopted by init
Summary: A zombie is a terminated process whose exit status has not been collected by its parent. An orphan is an active process whose parent has terminated.

8. Cascading Termination

  • Some OSs do not allow children to continue after the parent terminates.

Definition

Termination of a parent causes termination of:

Child → Grandchild → Further descendants

The OS initiates this termination.

9. Interprocess Communication (IPC)

Definition

IPC = communication between processes.

Processes may be:

  • Independent → cannot affect each other.
  • Cooperating → can affect/be affected by other processes.

Why processes cooperate?

  • Information sharing
  • Computation speed-up
  • Modularity
  • Convenience

Two main IPC models

  1. Shared Memory
  2. Message Passing

10. Shared Memory

  • A memory area is shared by multiple processes.
  • Processes communicate through shared memory.
  • Communication is mainly controlled by user processes, not the OS.
  • Processes must synchronize access to shared data.
Key Consideration: Explicit synchronization is required when multiple processes write to shared memory.

11. Message Passing

  • Processes communicate without shared variables.

Basic operations

  • send(message)
  • receive(message)

Used for communication and synchronization. Message size can be fixed or variable.

Summary:
Shared Memory: Direct access to shared data structures.
Message Passing: Communication via explicit send and receive operations.

12. Remote Procedure Call (RPC)

  • RPC = mechanism that makes procedure calls between processes on networked systems appear simpler.
  • Uses ports for service differentiation.
  • Client stub acts as a proxy. Locates server and marshals parameters.
  • Server stub receives, unpacks parameters, and performs the procedure.
Client Stub: Locates server and marshals parameters.
Server Stub: Unpacks parameters and invokes the execution.

13. Pipes

Definition: A pipe is a communication channel between processes.

Important questions:

  • Unidirectional or bidirectional?
  • Half-duplex or full-duplex?
  • Parent-child relationship required?
  • Can it work over a network?

13.1 Ordinary Pipes

  • Usually used between parent and child.
  • Unidirectional.
  • Producer writes → Consumer reads.
  • Producer = write end; Consumer = read end.
  • In Windows, called anonymous pipes.
Note: Unused pipe ends must be closed to prevent processes from blocking indefinitely.

13.2 Named Pipes

  • Bidirectional
  • No parent-child relationship required
  • Multiple processes can use them
  • Available in UNIX and Windows

Ordinary vs Named Pipe

Ordinary Pipe Named Pipe
Usually parent-child No parent-child requirement
Unidirectional Bidirectional
Less powerful More powerful
Anonymous Has a name

14. Threads

Definition: A thread is a unit of execution within a process.

Modern applications are generally multithreaded.

Example: Thread 1 → UI | Thread 2 → Network requests | Thread 3 → JavaScript | Thread 4 → File download

Process vs Thread

  • Processes: Heavyweight units with distinct memory spaces.
  • Threads: Lightweight execution units sharing process memory space.

Threads can simplify programs and improve efficiency.

15. Benefits of Multithreading

  1. Responsiveness: One blocked part does not necessarily stop the whole application.
  2. Resource Sharing: Threads of the same process naturally share process resources.
  3. Economy: Thread creation and switching cost less than process creation and context switching.
  4. Scalability: Threads can use multiprocessor/multicore systems.
Key Benefits: Responsiveness, Resource Sharing, Economy, and Scalability.

16. Concurrency vs Parallelism

Concurrency

  • Multiple tasks make progress during overlapping periods.
  • Possible even on a single-core CPU through scheduling.

Parallelism

  • Multiple tasks are executed simultaneously.
  • Requires multiple cores/processors for true simultaneous execution.
Concurrency Parallelism
Tasks make progress Tasks execute simultaneously
Possible on single core Uses multiple cores
Scheduler can switch tasks Tasks can run at same time
Key Distinction: Concurrency allows multiple tasks to make progress over overlapping time frames; parallelism executes multiple tasks simultaneously.

17. Types of Parallelism

Data Parallelism

  • Same operation on different data chunks using multiple cores/threads.
  • Example: Split an array into parts and process all parts simultaneously.

Task Parallelism

  • Different threads perform different operations.
  • Example: One thread downloads data while another processes it.
Summary:
Data Parallelism: Same operation applied across different data chunks.
Task Parallelism: Different operations executed concurrently on separate threads.

18. Multicore Programming Challenges

Main challenges:

  • Dividing activities
  • Load balancing
  • Data splitting
  • Data dependency
  • Testing and debugging

19. User Threads vs Kernel Threads

User Threads

  • Managed by a user-level thread library.
  • Examples of thread libraries: POSIX Pthreads, Windows threads, Java threads

Kernel Threads

  • Supported and managed by the OS kernel.
  • Examples: Windows, Linux, Solaris, Mac OS X, Tru64 UNIX

20. Blocking: User vs Kernel Threads

User Thread

If one user thread makes a blocking system call:

One thread blocks → Entire process may block → All user threads stop

Kernel Thread

If one kernel thread blocks:

Only that thread blocks → Other threads can continue

Key Distinction: A blocking system call in a user thread blocks the entire process, whereas in a kernel thread, only that thread is blocked.

21. Multithreading Models

Three main models: Many-to-One, One-to-One, Many-to-Many

21.1 Many-to-One Model

Many user threads → One kernel thread

  • One blocking thread can block all.
  • No true parallelism on multicore systems.
  • Rarely used today.
  • Examples: Solaris Green Threads, GNU Portable Threads
Summary: Multiple user threads mapped to a single kernel thread can cause potential bottlenecks during blocking operations.

21.2 One-to-One Model

One user thread → One kernel thread

  • More concurrency than many-to-one.
  • Creating a user thread also creates a kernel thread.
  • Number of threads may be restricted because of overhead.
  • Examples: Windows, Linux, Solaris 9+
Summary: Each user thread maps to a distinct kernel thread, maximizing concurrency but incurring kernel overhead.

21.3 Many-to-Many Model

Many user threads → Many kernel threads

  • OS creates an appropriate number of kernel threads.
  • Provides greater flexibility.
  • Examples: Solaris versions before 9, Windows with ThreadFiber package
Summary: Maps many user threads to an equal or lesser number of kernel threads, balancing concurrency and resource usage.

22. Multithreading in Python

Basic Thread

import threading
        
        def task():
            print("Hello from thread")
        
        t = threading.Thread(target=task)
        t.start()
        t.join()
        
        print("Main thread finished")

Important methods:

  • Thread(...) → creates thread
  • start() → starts execution
  • join() → waits for thread completion

23. Creating Multiple Threads

import threading
        
        def worker(n):
            print(f"Thread {n} is running")
        
        threads = []
        
        for i in range(5):
            t = threading.Thread(target=worker, args=(i,))
            threads.append(t)
            t.start()
        
        for t in threads:
            t.join()
        
        print("All threads completed")

Execution Flow: Create → Start → Join

24. Shared Data and Race Conditions

When multiple threads access the same variable, incorrect results may occur due to unsynchronized access.

Example shared variable:

counter = 0

Two threads may simultaneously execute:

counter += 1

This can create a race condition.

Race Condition: When the final result depends on the timing/order of thread execution.

25. Synchronizing Shared Data with Locks

import threading
        
        counter = 0
        lock = threading.Lock()
        
        def increment():
            global counter
            for _ in range(100000):
                with lock:
                    counter += 1

Lock Mechanism

  • Allows controlled access to shared data so that critical operations are protected.
  • Without Lock → possible race condition
  • With Lock → synchronized access

Operating Systems — CPU Scheduling (Week 3)

1. CPU Scheduling — Introduction

CPU Scheduling: Selecting a process from the ready queue and allocating the CPU to it.

Main Goals

  • Maximize CPU utilization
  • Maximize throughput
  • Minimize waiting time
  • Minimize turnaround time
  • Minimize response time

Why Scheduling is Needed

With multiprogramming, when one process waits for I/O, another process can use the CPU.

        Process P1:  CPU  ──>  I/O  ──>  CPU  ──>  I/O  ──>  CPU
                                     │
                                     ▼
        Process P2:            CPU  ──>  I/O  ──>  CPU

2. Basic Concepts

CPU–I/O Burst Cycle

A process normally alternates between:

CPU Burst → I/O Burst → CPU Burst → I/O Burst → ...

  • CPU Burst: Process executes instructions on CPU.
  • I/O Burst: Process waits for I/O operation.

The distribution of CPU-burst times is important for scheduling.

Fingertip Summary: Process execution = CPU execution + I/O waiting

3. Context Switching

Context Switch: Switching the CPU from one process to another.

        Process P1                             Process P2
            │                                      │     
            │            CPU execution             │     
            ├─────────────────────────────────────►│     
            │                                      │     
            │           Context Switch             │     
            ├─────────────────────────────────────►│     
            │                                      │     
            │                              CPU execution

During a context switch:

  1. Save the state of the current process.
  2. Load the state of the next process.
  3. Start/resume the next process.
Important: Context switching is overhead because the CPU does not perform useful process work during the switch.

4. Scheduling Criteria

Criterion Meaning Goal
CPU Utilization Percentage of time CPU is busy Maximize
Throughput Processes completed per unit time Maximize
Turnaround Time Total time from arrival to completion Minimize
Waiting Time Time spent waiting in ready queue Minimize
Response Time Time from request submission until first response Minimize
Important Formula: Turnaround Time = Completion Time - Arrival Time

Response Time

  • Response time measures the time until the first response, not the complete output.
  • Especially important in time-sharing/interactive systems.

5. Scheduling Algorithm Optimization

A good scheduling algorithm tries to achieve:

  • CPU Utilization → MAX
  • Throughput → MAX
  • Turnaround Time → MIN
  • Waiting Time → MIN
  • Response Time → MIN

6. First-Come, First-Served (FCFS) Scheduling

FCFS: The process that arrives first gets the CPU first.

  • Non-preemptive
  • Simple to implement
  • Uses FIFO ordering

Example

Process Burst Time
P1 24
P2 3
P3 3

Case 1: Arrival order: P1 → P2 → P3

        Gantt Chart
        0                24       27       30
        ┌────────────────┬────────┬────────┐
        │       P1       │   P2   │   P3   │
        └────────────────┴────────┴────────┘
  • Waiting Time: P1 = 0, P2 = 24, P3 = 27
  • Average Waiting Time: (0 + 24 + 27) / 3 = 17

Case 2: Arrival order: P2 → P3 → P1

        Gantt Chart
        0        3        6                30
        ┌────────┬────────┬────────────────┐
        │   P2   │   P3   │       P1       │
        └────────┴────────┴────────────────┘
  • Waiting Time: P1 = 6, P2 = 0, P3 = 3
  • Average Waiting Time: (6 + 0 + 3) / 3 = 3
Exam Point: FCFS performance can change significantly depending on arrival order (Convoy Effect).

7. Shortest-Job-First (SJF) Scheduling

SJF: Select the process having the shortest next CPU burst.

Features

  • Usually non-preemptive
  • Gives minimum average waiting time for a given set of processes.
  • Main difficulty: predicting the length of the next CPU burst.
Important: SJF is optimal for minimum average waiting time under the standard assumptions.

SJF Example

Process Arrival Time Burst Time
P1 0 6
P2 2 8
P3 4 7
P4 5 3 
        Gantt Chart
        0        6        9               16              24
        ┌────────┬────────┬───────────────┬───────────────┐
        │   P1   │   P4   │       P3      │       P2      │
        └────────┴────────┴───────────────┴───────────────┘
  • Waiting Time: P1 = 0, P2 = 16 - 2 = 14, P3 = 9 - 4 = 5, P4 = 6 - 5 = 1
  • Average Waiting Time: (0 + 14 + 5 + 1) / 4 = 5

8. Determining the Next CPU Burst

The exact length of the next CPU burst is generally not known. Therefore, it is estimated from previous CPU bursts.

Exponential Averaging

A common prediction formula is:

τ(n+1) = α · t(n) + (1 - α) · τ(n)

  • τ(n+1) = predicted next CPU burst
  • t(n) = actual previous CPU burst
  • τ(n) = previous predicted burst
  • α = weighting factor (Commonly, α = 1/2)

Previous CPU bursts → Estimate next burst → Choose shortest predicted burst

9. Shortest-Remaining-Time-First (SRTF)

SRTF = Preemptive version of SJF

The CPU is given to the process with the shortest remaining CPU burst.

If a new process arrives with a shorter remaining time: Current Process → Preempt → New shorter process

Key Difference

Feature SJF SRTF
Type Usually non-preemptive Preemptive
Execution Runs selected process until completion/block Can interrupt current process
Decision Criterion Based on shortest burst Based on shortest remaining burst

10. SRTF Example

Process Arrival Time Burst Time
P1 0 8
P2 1 4
P3 2 9
P4 3 5 
        Scheduling Idea / Gantt Chart
        Time:
        0    1        5        10       17       26

Exam Point: SRTF can improve waiting time but causes more context switches because of preemption.

11. Priority Scheduling

Each process is assigned a priority number.

Smaller priority number → Higher priority

Example: Priority 1 > Priority 2 > Priority 3

The highest-priority process gets the CPU.

Types

  • Preemptive Priority Scheduling
  • Non-preemptive Priority Scheduling

Relation with SJF

SJF can be considered a priority scheduling algorithm where: Shorter predicted CPU burst → Higher priority

Problem: Starvation

Starvation: A low-priority process may wait indefinitely because higher-priority processes keep arriving.

High Priority → CPU | High Priority → CPU | Low Priority → Waiting...

Solution: Aging

Aging: Gradually increase the priority of a waiting process.

Long waiting time → Priority increases → Eventually gets CPU

12. Priority Scheduling Example

Process Burst Time Priority
P1 10 3
P2 1 1
P3 2 4
P4 1 5
P5 5 2

Priority order: P2 → P5 → P1 → P3 → P4

Exam Point: Priority 1 is higher than Priority 5 when smaller numbers represent higher priority.

13. Round Robin (RR) Scheduling

Round Robin: Each process receives a fixed amount of CPU time called the time quantum (q).

Typical quantum: q = 10–100 ms

When the quantum expires:

Running Process → Preempt → End of Ready Queue

Example Queue: P1 → P2 → P3 → P1 → P2 → P3 → ...

If there are n processes:

  • Each process gets approximately 1/n of CPU time.
  • A process waits for at most approximately (n - 1)q before getting another turn (assuming standard RR queue).

14. Round Robin Performance

  • Large Time Quantum (q large): RR approaches FCFS/FIFO.
  • Small Time Quantum (q small): More context switches → Higher overhead.

Therefore, Time Quantum should be large compared with context-switch time.

  • Typical values: q = 10–100 ms
  • Context switch: < 10 μs
Key Point: RR generally provides better response time than FCFS and is suitable for interactive systems.

P2 3
P3 3

With q = 4:

16. Time Quantum vs Context Switch

Large q Small q
Less switching More switching
Less overhead More overhead
RR → FCFS Better response time
Rule of Thumb: About 80% of CPU bursts should ideally be shorter than q. This allows most CPU bursts to finish within one quantum.

17. Multilevel Queue Scheduling

The ready queue is divided into separate queues. Example:

  • Foreground Queue (Interactive): Uses RR
  • Background Queue (Batch): Uses FCFS
Important: A process is permanently assigned to one queue. Each queue can have its own scheduling algorithm.

Scheduling Between Queues

  1. Fixed Priority: Serve foreground completely → Background. (Problem: Background processes may suffer from starvation.)
  2. Time Slicing: CPU time is divided between queues. (Example: 80% CPU to Foreground RR, 20% CPU to Background FCFS. Allows both queues to receive CPU time.)

18. Multilevel Feedback Queue (MLFQ)

MLFQ: Processes can move between different queues based on their behavior.

Basic Rules

  • New process → Top-priority queue
  • If it uses entire quantum: Move to Lower-priority queue
  • If it waits for I/O before quantum expires: Stays in same queue

Aging

A process waiting too long in a lower queue can be promoted.

Long waiting → Priority increases → Move upward

19. MLFQ Example

Three queues:

  • Q0 → RR, q = 8 ms
  • Q1 → RR, q = 16 ms
  • Q2 → FCFS

Scheduling Flow

New Job → Q0 (8 ms) → [If not finished] → Q1 (16 ms) → [If not finished] → Q2 (FCFS)

20. MLFQ Philosophy

MLFQ does not initially know whether a process is short or long. Therefore:

New process → Assume short → Give high priority

  • Short job: Finishes quickly at the top.
  • Long job: Moves down queues and runs as a batch-like job.
Key Idea: Short/interactive jobs stay high. Long CPU-bound jobs gradually move lower.

21. MLFQ — Interactive vs CPU-Bound Jobs

  • Interactive Job (short CPU bursts):
    High-priority queue → Finishes quickly
  • CPU-bound Job (long CPU bursts):
    Uses entire quantum → Moves downward → Lower-priority queue

22. MLFQ Major Problems and Solutions

Problem 1: Too Many Interactive Jobs

If too many interactive jobs remain in high-priority queues, they consume most CPU time, leading to starvation for long-running jobs.

  • Solution: Periodic Priority Boost. After some time period S, move all jobs to the topmost queue. This prevents long-running processes from being permanently ignored.

Problem 2: Gaming the Scheduler

A process might deliberately give up the CPU before its quantum expires to remain in a high-priority queue.

  • Solution: Track Total Time. Track the total time allotment used at a level. If it uses full time allotment (even across multiple short bursts) → Priority reduced. The process cannot stay at a high priority simply by giving up the CPU early.

23. Impact of CPU Scheduling on AI/ML Workloads

CPU scheduling is particularly important in modern AI/ML systems because CPU, GPU, memory, storage, and network operations are interconnected.

A. Mixed Compute and I/O Phases

AI workloads can alternate between different types of work:

Data decoding (CPU) → Forward/Backward Passes (GPU) → Checkpointing (I/O)

  • CPU-heavy: Data decoding, Data augmentation, Tokenization
  • GPU-heavy: Forward pass, Backward pass
  • I/O-heavy: Disk operations, Network operations, Checkpointing

Scheduling Impact

Poor CPU scheduling can create a phase mismatch:

CPU delayed → Data not prepared → GPU waits → GPU pipeline stalls

Key Point: Efficient CPU scheduling helps keep GPU workloads continuously supplied with data.

24. Bursty and Synchronized AI/ML Execution

Distributed DNN training commonly uses synchronization operations such as All-reduce or All-gather. Workers may need to reach a synchronization barrier together.

        Worker 1 ──┐                  
        Worker 2 ──┼──► Barrier ──> Continue
        Worker 3 ──┤                  
        Worker 4 ──┘

If one process is delayed (straggler problem):

        Worker 1 ──┐          
        Worker 2 ──┼──► Waiting
        Worker 3 ──┤          
        Worker 4 ──┘

Delayed Worker → Barrier delayed → Other GPUs wait

Exam Point: In synchronized distributed training, scheduling delays affecting one worker can cause other workers/GPUs to remain idle.

25. Latency-Sensitive AI Inference

Some AI workloads require very low response latency.

  • Examples: First-token latency, Autoregressive decoding loops, RPC handling threads

Scheduling Impact

If an inference thread is preempted or its time slice expires:

Preemption → Inference thread waits → Response delayed → Higher tail latency

Operating Systems — Concurrency, Synchronization & Deadlocks

1. Concurrency and Synchronization

1.1 Concurrency

  • Concurrency = Multiple processes/threads execute during overlapping time periods.
  • When processes share data/resources, incorrect results can occur unless their access is properly synchronized.
  • Synchronization = Coordinating processes so that shared data remains consistent.

2. Producer-Consumer Problem

The Producer-Consumer Problem is a classic synchronization problem involving a shared buffer.

        Shared Buffer
        +-------------------------------+--------+
        Producer | [ ][ ][ ][ ][ ] Buffer | Consumer
         --->    | Adds data     Removes data |  --->   
        +-------------------------------+--------+
  • Producer: Generates data and puts it into the shared buffer.
  • Consumer: Takes data from the shared buffer and processes it.

Main Challenges

  • Producer must not add data when the buffer is full.
  • Consumer must not remove data when the buffer is empty.
  • Producer and consumer must not access the buffer in a conflicting way at the same time.

2.1 Producer Code

while (true) {
            /* produce an item in next_produced */
            while (counter == BUFFER_SIZE)
                ; /* do nothing */
        
            buffer[in] = next_produced;
            in = (in + 1) % BUFFER_SIZE;
            counter++;
        }

2.2 Consumer Code

while (true) {
            while (counter == 0)
                ; /* do nothing */
        
            next_consumed = buffer[out];
            out = (out + 1) % BUFFER_SIZE;
            counter--;
        
            /* consume the item in next_consumed */
        }
Important: counter = Number of items currently present in the buffer.
counter = 0 → Buffer Empty
0 < counter < N → Buffer Partially Full
counter = N → Buffer Full

3. Race Condition

Definition

A Race Condition occurs when multiple processes access and modify shared data concurrently, and the final result depends on the order in which their instructions execute.

Example

Suppose counter = 5

counter++ may internally execute as:

register1 = counter
        register1 = register1 + 1
        counter = register1

counter-- may internally execute as:

register2 = counter
        register2 = register2 - 1
        counter = register2

Problematic Interleaving

        Initial: counter = 5
        
        S0: Producer -> register1 = counter          (register1 = 5)
        S1: Producer -> register1 = register1 + 1    (register1 = 6)
        S2: Consumer -> register2 = counter          (register2 = 5)
        S3: Consumer -> register2 = register2 - 1    (register2 = 4)
        S4: Producer -> counter = register1          (counter = 6)
        S5: Consumer -> counter = register2          (counter = 4)
  • Expected Result: One increment and one decrement should cancel each other (5 + 1 - 1 = 5).
  • Actual Result: counter = 4 (The shared variable has become inconsistent).
Exam Point: Race conditions occur because operations on shared data can be interleaved unpredictably.

4. Critical Section Problem

4.1 Critical Section

A Critical Section (CS) is the part of a process where shared resources/data are accessed or modified.

Examples: Updating common variables, Updating a shared table, Writing to a shared file, Accessing a shared buffer.

If one process is executing its critical section, another process should not execute its conflicting critical section simultaneously.

4.2 General Process Structure

        +---------------------+
        |    Entry Section    |
        |   (Request access)  |
        +----------+----------+
                   |
                   v
        +---------------------+
        |   Critical Section  |
        |   (Shared resource) |
        +----------+----------+
                   |
                   v
        +---------------------+
        |    Exit Section     |
        |   (Release access)  |
        +----------+----------+
                   |
                   v
        +---------------------+
        |  Remainder Section  |
        |     (Other work)    |
        +---------------------+
Section Purpose
Entry Request permission to enter CS
Critical Access shared resource
Exit Release/leave CS
Remainder Execute other code

5. Requirements for Critical-Section Solution

A correct solution must satisfy three requirements.

5.1 Mutual Exclusion

If process Pi is executing in its critical section, no other process can execute its critical section at the same time.

P0 → [ CRITICAL SECTION ] | P1 → Cannot enter CS

5.2 Progress

If no process is currently in the critical section and some processes want to enter, the selection of the next process cannot be postponed indefinitely.

5.3 Bounded Waiting

There must be a limit on how many times other processes can enter their critical sections after a process has requested entry and before its request is granted.

Assumptions: Each process executes at a nonzero speed. No assumption is made about the relative speed of processes.

Fingertip:
Mutual Exclusion → Only one inside CS
Progress → Don't postpone entry forever
Bounded Waiting → Don't make a process wait forever

6. Peterson's Solution

Peterson's Solution is an algorithmic solution to the critical-section problem for two processes.

  • Assumes: Two processes (P0 and P1). Load/store instructions are atomic.

Two shared variables are used:

int turn;
        Boolean flag[2];
  • turn: Indicates whose turn it is to enter the critical section.
  • flag[i]: Indicates whether process Pi wants to enter the critical section (flag[i] = true).

6.1 Peterson's Algorithm for P0

do {
            flag[0] = true;
            turn = 1;
        
            while (flag[1] && turn == 1)
                ;
        
            // critical section
        
            flag[0] = false;
        
            // remainder section
        } while (true);

6.2 Peterson's Algorithm for P1

do {
            flag[1] = true;
            turn = 0;
        
            while (flag[0] && turn == 0)
                ;
        
            // critical section
        
            flag[1] = false;
        
            // remainder section
        } while (true);

6.3 Why Peterson's Solution Works

  1. Mutual Exclusion: P0 enters CS only when flag[1] == false OR turn == 0. The while condition ensures that both cannot enter simultaneously.
  2. Progress: P0 waits only when flag[1] == true AND turn == 1. If the other process does not want to enter, P0 can proceed.
  3. Bounded Waiting: Once a process sets its flag to true, the other process can enter the critical section at most one more time before the waiting process gets its turn.
Fingertip: Peterson's Solution
• flag[] → Who wants to enter?
• turn → Whose turn?
• Two-process solution
• Satisfies: Mutual Exclusion, Progress, Bounded Waiting

7. Mutex Locks

Definition

A Mutex Lock is a synchronization mechanism used to protect a critical section.

A process must acquire and release a mutex lock around its critical section:

acquire() → Critical Section → release()

The lock is represented by a Boolean-like variable indicating whether it is available.

7.1 acquire() and release()

acquire() {
            while (!available)
                ; /* busy wait */
            available = false;
        }
        
        release() {
            available = true;
        }

Important: acquire() and release() must be atomic (generally implemented using hardware atomic instructions).

7.2 Spinlock

Mutex locks using busy waiting are called spinlocks. CPU time is wasted while waiting.

Important Rule: The same thread/process that performs acquire() should perform release().

8. Semaphore

Definition

A Semaphore is a synchronization tool that provides more sophisticated process synchronization than simple mutex locks. A semaphore S is an integer variable accessed only through atomic operations:

  • wait(S) (Originally P())
  • signal(S) (Originally V())

8.1 wait()

wait(S) {
            while (S <= 0)
                ; /* busy wait */
            S--;
        }

8.2 signal()

signal(S) {
            S++;
        }
Fingertip:
wait() → Decrease semaphore / wait if unavailable
signal() → Increase semaphore / release resource

9. Types of Semaphores

Type Values Typical Use
Counting Semaphore 0, 1, 2, 3, ... Multiple instances of a resource
Binary Semaphore 0 or 1 Mutual exclusion (like a mutex lock)

10. Semaphore for Process Ordering

Suppose S1 must happen before S2. Create: semaphore synch = 0;

        P1:                 P2:
            S1;                 wait(synch);
            signal(synch);      S2;

S1 → signal(synch) → wait(synch) → S2

Therefore: S1 always happens before S2.

11. Deadlock & 12. Example Using Semaphores

Definition

Deadlock occurs when two or more processes wait indefinitely for events/resources that can only be caused/released by the waiting processes.

Simple Example

Initially: S = 1, Q = 1

        P0                  P1
        wait(S)             wait(Q)
           |                   |
           v                   v
        holds S             holds Q
           |                   |
        wait(Q)             wait(S)
           |                   |
           v                   v
         WAIT                WAIT
  • P0 holds S and waits for Q.
  • P1 holds Q and waits for S.
  • Neither process can continue.

13. Starvation

Definition

Starvation = Indefinite blocking of a process. A process may wait indefinitely because it is never selected or removed from the semaphore/resource waiting queue.

Deadlock vs Starvation

Deadlock Starvation
Processes wait for each other A process waits indefinitely
Usually involves circular waiting Can occur due to unfair scheduling
Multiple processes permanently blocked One process may continuously be denied access
Fingertip:
Deadlock → Everyone involved is stuck
Starvation → A process may never get its turn

14. Necessary Conditions for Deadlock

Deadlock can occur only when all four conditions hold simultaneously:

                   +----------------------+----------------------+
                   |                      |                      |
                   v                      v                      v
            Mutual Exclusion        Hold & Wait            No Preemption
                                      |
                                      v
                                Circular Wait

14.1 Mutual Exclusion

At least one resource must be non-sharable. Only one process can use that resource at a time.

14.2 Hold and Wait

A process is holding at least one resource while waiting to acquire another resource held by another process.

14.3 No Preemption

A resource cannot be forcibly taken away from a process. It must be released voluntarily by the process holding it.

14.4 Circular Wait

A circular chain of waiting processes exists:

P0 waits for R1 (held by P1) → P1 waits for R2 (held by P2) → P2 waits for R3 (held by P0)

Exam Point: Deadlock requires ALL FOUR conditions to hold simultaneously.

15. Traffic Example of Deadlock

A traffic intersection jam demonstrates all four deadlock conditions:

               Vehicle A
                   |
                   v
             +-----------+
             |   Road    |
             +-----------+
                   |
                   v
                Vehicle B
                   |
                   v
                Vehicle C ---> (Waiting in circular chain)
  1. Mutual Exclusion: Only one vehicle can occupy a particular road section at a time.
  2. Hold and Wait: Each vehicle occupies one section while waiting for another section.
  3. No Preemption: A road section occupied by a vehicle cannot simply be taken away.
  4. Circular Wait: Each vehicle waits for a section occupied by another vehicle in the circular chain.

16. Methods for Handling Deadlocks

There are four major approaches to handling deadlocks:

  1. Deadlock Prevention: Prevent at least one of the four necessary conditions from occurring.
  2. Deadlock Avoidance: Use additional information about future resource requirements and allocate resources only if the resulting state remains safe.
  3. Deadlock Detection and Recovery: Allow deadlocks to occur, detect them, and then recover.
  4. Do Nothing: If a system does not use prevention, avoidance, or detection/recovery, deadlocks may occur and remain.

17. Deadlock Prevention

Deadlock prevention works by restricting how resources can be requested. The goal is to ensure that at least one necessary condition cannot hold.

17.1 Prevent Mutual Exclusion

  • Cannot always be eliminated (non-sharable resources require mutual exclusion).
  • For sharable resources (e.g., read-only files), sharing is possible.

17.2 Prevent Hold and Wait

  • Require a process to request all required resources before execution begins, OR
  • Allow a process to request resources only when it currently holds no resources.
  • Disadvantages: Low resource utilization, starvation may occur.

18. Deadlock Prevention — No Preemption

If a process holding some resources requests another resource that cannot be immediately allocated, then all resources currently held by that process may be released.

P0 (Holds R1+R2) → Requests R3 (Unavailable) → Release R1+R2 → Wait for R1+R2+R3 → Restart when all obtained

  • Currently held resources are released.
  • Preempted resources are added to the list of resources for which the process is waiting.
  • The process restarts only when it can regain its old resources and the newly requested resources.

19. Deadlock Prevention — Circular Wait

Circular wait can be prevented by imposing a total ordering on all resource types. Each resource type is assigned a number (e.g., Tape=1, Disk=5, Printer=12).

Rule: A process must request resources in increasing order. If it has requested Ri, it can request Rj only if F(Rj) > F(Ri).

  • Valid: Tape drive (1) → Disk drive (5) → Printer (12)
  • Invalid: Printer (12) → Disk drive (5) (because 5 < 12)
Exam One-Liner: Circular wait is prevented by imposing a total ordering on resource types and requiring every process to request resources in increasing order.

20. Deadlock Avoidance

Deadlock Avoidance requires additional information about the maximum resources each process may need. The OS dynamically checks every resource request.

        Process Requests Resource
                   |
                   v
         Check Resulting State
                   |
        +-----------------+-----------------+
        |                                   |
        v                                   v
        Safe State                     Unsafe State
        (Allocate Resource)               (Wait)
  • Each process must declare its maximum resource requirement in advance.
  • The system decides whether granting a request keeps the system in a safe state.

21. Resource-Allocation State & 22. Safe State & 23. Safe vs Unsafe

Resource-Allocation State: Defined by available resources, allocated resources, and maximum resource demands.

Safe State

A system is in a safe state if there exists an ordering of all processes <P1, P2, ..., Pn> (a safe sequence) such that every process can obtain its remaining required resources, finish, and release its resources.

Available Resources → Can P1 finish? (Yes) → P1 finishes & releases → Can P2 finish?...

Safe vs Unsafe State

State Meaning
Safe State System has at least one safe sequence (No deadlock)
Unsafe State No guaranteed safe sequence (Deadlock is possible)
Deadlock State Processes are actually permanently blocked
Fingertip:
Safe → Deadlock guaranteed to be avoidable
Unsafe → Deadlock may occur
Deadlock → Deadlock has occurred

24. Banker's Algorithm & 25. System Model

Banker's Algorithm is a deadlock-avoidance algorithm.

  • Used when multiple instances of each resource type exist.
  • Each process declares its maximum resource requirement.
  • A process may need to wait for resources, and must eventually return all allocated resources.

System Model: A process uses resources in this order: Request → Use → Release

26. Banker's Algorithm Example & 27. Need Matrix

5 processes (P0-P4), 3 resource types (A=10, B=5, C=7).

Snapshot at T0: Available = (3, 3, 2)

Need Matrix

Need = Max - Allocation

Process Allocation (A B C) Max (A B C) Need (A B C)
P0 0 1 0 7 5 3 7 4 3
P1 2 0 0 3 2 2 1 2 2
P2 3 0 2 9 0 2 6 0 0
P3 2 1 1 2 2 2 0 1 1
P4 0 0 2 4 3 3 4 3 1

28. Safe Sequence in Banker's Algorithm

Initial: Available = (3, 3, 2)

  1. P1: Need (1,2,2) ≤ Available (3,3,2) → Finishes. New Available = (3,3,2) + (2,0,0) = (5,3,2)
  2. P3: Need (0,1,1) ≤ Available (5,3,2) → Finishes. New Available = (5,3,2) + (2,1,1) = (7,4,3)
  3. P4: Need (4,3,1) ≤ Available (7,4,3) → Finishes. New Available = (7,4,3) + (0,0,2) = (7,4,5)
  4. P2: Need (6,0,0) ≤ Available (7,4,5) → Finishes. New Available = (7,4,5) + (3,0,2) = (10,4,7)
  5. P0: Need (7,4,3) ≤ Available (10,4,7) → Finishes.
Safe sequence: <P1, P3, P4, P2, P0>
Hence: System is in a SAFE STATE

29. Banker's Algorithm — Fingertip Method

  1. Calculate Need: Need = Max - Allocation
  2. Start with Available
  3. Find a process where Need <= Available
  4. Assume it finishes
  5. Add its Allocation to Available
  6. Repeat

If ALL processes finish → SAFE STATE. If no process can finish → UNSAFE STATE.

32. Most Important Exam Concepts

  • Critical Section: Entry → Critical → Exit → Remainder
  • Three CS Requirements: Mutual Exclusion, Progress, Bounded Waiting
  • Peterson's Solution: Two processes, flag[], turn
  • Mutex: acquire() → Critical Section → release()
  • Semaphore: wait(S), signal(S)
  • Deadlock Conditions: Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait
  • Deadlock Prevention: Break at least ONE necessary condition
  • Deadlock Avoidance: Never enter an unsafe state
  • Banker's Algorithm: Need = Max - Allocation
  • Safe State: At least one safe sequence exists

33. Exam One-Liners

  • Race Condition: A situation where the final result depends on the order of concurrent execution of processes.
  • Critical Section: The part of a process that accesses shared data/resources.
  • Mutual Exclusion: Only one process can execute a critical section at a time.
  • Progress: If the critical section is free, selection of the next process cannot be postponed indefinitely.
  • Bounded Waiting: A process must have a finite bound on how many times others can enter before it gets its turn.
  • Peterson's Solution: A software solution for the critical-section problem involving two processes using flag[] and turn.
  • Mutex Lock: A synchronization mechanism that protects a critical section using acquire() and release().
  • Spinlock: A lock where a process continuously waits by busy waiting.
  • Semaphore: An integer synchronization variable accessed through atomic wait() and signal() operations.
  • Deadlock: A state where processes wait indefinitely for resources/events held or controlled by other waiting processes.
  • Starvation: Indefinite waiting of a process because it is repeatedly denied access to a resource.
  • Deadlock Prevention: Preventing at least one of the four necessary deadlock conditions.
  • Deadlock Avoidance: Dynamically allocating resources while ensuring the system remains in a safe state.
  • Safe State: A state in which there exists a safe sequence allowing all processes to finish.
  • Banker's Algorithm: A deadlock-avoidance algorithm that checks whether granting resources keeps the system safe.
  • Need Matrix: Need = Max - Allocation.
  • Circular Wait Prevention: Assign a numerical order to resource types and require processes to request resources in increasing order.
  • No Preemption Prevention: If a requested resource cannot be immediately allocated, a process may be forced to release resources it currently holds.

35. Ultimate Fingertip Memory Lines

  • Producer-Consumer = Shared buffer synchronization problem
  • Race Condition = Result depends on execution order
  • Critical Section = Shared-resource access code
  • Mutex = Lock before CS, unlock after CS
  • Semaphore = wait() + signal()
  • Peterson = flag[] + turn
  • Deadlock = Processes permanently wait for each other
  • Deadlock Conditions = Mutual Exclusion + Hold and Wait + No Preemption + Circular Wait
  • Prevention = Break at least one condition
  • No Preemption = Release held resources if new resource cannot be obtained
  • Circular Wait Prevention = Request resources only in increasing order
  • Avoidance = Never enter unsafe state
  • Safe State = Safe sequence exists
  • Banker's Algorithm = Need = Max - Allocation
